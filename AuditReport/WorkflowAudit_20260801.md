# 组牌优化工作流回归审计（2026-08-01）

## 结论

工作流已经能指导人工完成一次有约束的牌表优化，但目前仍是提示词/检查清单，不是可执行、可复现、可比较的 AI 优化系统。本次从 V1 得到了合法的 V5 牌表，也成功发现了结构缺口；但 API 调用、候选归并、评分、概率、换备和运行证据都依赖临时人工操作，尚不能稳定批量运行。

建议的产品边界是：确定性程序负责数据、规则、约束、统计与版本；AI 负责主题理解、候选解释、多方案取舍与对局推演。不能让模型凭自然语言声明代替机器门禁。

## 已发现问题

### P0：会直接造成错误结果

1. **颜色过滤错误**：原文把纯绿写成 `ci:g`，会排除纯绿套牌合法使用的无色牌，例如 Scavenger Grounds、The Stone Brain。默认应为 `ci<=g`；只有明确要求牌张身份必须恰为绿色时才用 `ci:g`。
2. **BO1/BO3 未建模**：MTGA 存在队列专属禁牌；BO1 没有局间换备，但当前 Arena 仍可提供至多 15 张供“游戏外”效果使用。只写“MTGA 先驱”不能唯一确定合法性、备牌用途和交付格式。
3. **发售日只靠人工排除**：`/cards/named` 本次对 Forest 返回了 2026-08-14 的 HOB 未来印刷。每个搜索都必须加 `date<=基准日期`，不能只在看到异常时手工 `-e:set`。
4. **平台可用性容易误判**：Ram Through、Scavenger Grounds、Topiary Stomper、Cultivator Colossus 等牌的最新印刷不一定带 Arena 字段，但旧印刷可用。必须在 oracle 级合法性通过后检查所有印刷中的任一 `arena_id`。
5. **地当量定义混淆**：原公式把“真地 + MDFC×0.75 + 找地牌”都称为地当量，会把铺地咒语重复计入地源。起手地源、加权地当量、找地到手、找地进场、额外下地必须分栏。

### P1：阻碍可复现和自动优化

1. **没有执行器**：仓库中没有牌表 parser、API client、分页、缓存、重试、断点续跑、结构化输出或失败退出码。V2-V4 的“全部通过”没有机器可读证据。
2. **没有运行清单**：缺少基准日期、队列、查询式、响应抓取时间、原始结果哈希、失败/重试项和数据源版本，无法在数据更新后复现历史结果。
3. **没有统一卡牌模型**：普通牌、MDFC、历险、预备、通道、伪装的 face/mode 没有结构化表示；费用、角色和平台字段靠人工表格维护。
4. **没有约束求解器**：当前只检查 60/15，没有自动校验同名牌主备合计最多四张、基础地例外、颜色身份、禁牌、未发售牌、Arena 印刷和换备后仍为 60 张。
5. **没有优化目标**：主题保真、预期胜率、预算、复杂度、改动量之间没有权重。本次必须人工决定不把 V1 改造成主流獾地鼠中速，否则“优化”没有唯一含义。
6. **没有候选评分**：缺少费用段、角色替代、协同、独立强度、重复抽取风险、传奇密度、目标数量、卡差和互动密度等特征；目前只能人工浏览长候选列表。
7. **逐系列统计口径不完整**：oracle 去重后只保留一个印刷，再按该印刷的 set 分组，并不等价于逐系列遍历。需要同时保留 oracle 候选表和 print-set 命中关联表。
8. **第三方源没有健康策略**：mtgch 超时、模糊命中、分页、字段变化或中文名缺失时，没有超时、重试、精确名过滤、降级和人工复核状态。

### P2：影响优化质量

1. **没有起手/曲线概率**：应计算至少两地、关键回合三绿、抽到引擎/回报组合、基础地目标耗尽等概率，而不是只展示曲线。
2. **没有规则级互动校验**：费用检查只能发现“第五回合不能无加速施放六费牌”，不能判断 earthbend 是否重置地、召唤失调、触发时点、模式目标和替代效应。
3. **没有真实测试闭环**：典型对局目前是自然语言推演，没有 Arena 日志导入、对局标签、样本量、胜负原因、先后手和换备效果。
4. **环境数据过粗**：官方公告只能给大方向；缺少可配置的主流套牌样本、对局权重、常见去除/威胁和数据时间窗。
5. **换备不是约束对象**：需要为每个对局保存明确的换入/换出、主牌结构下限，以及 BO1 无局间换备但可能使用“游戏外”牌的分支。优化器可默认一换一维持 60 张；合法性只能要求主牌不少于 60、备牌不多于 15，不能强制数量相等。
6. **人工确认点阻塞批处理**：阶段 0 和阶段 3 要求等待用户，但回归测试需要“使用默认值并记录假设”的无人值守模式。

## 建议实现顺序

### 1. 确定性验证 CLI

输入 MTGA/MTGO 文本牌表，输出结构化 JSON 和 Markdown：规范化牌名、主备数量、同名张数、合法性、发售日、颜色、Arena 印刷、每面费用/文本、中文名、曲线和地源。任何硬错误返回非零退出码。

### 2. 数据层与运行清单

实现 Scryfall Collection 批查、Search 分页、限流、指数退避、磁盘缓存和 mtgch 降级；保存 `run.json`、原始响应缓存和查询哈希。测试固定使用快照，刷新数据作为显式操作。

### 3. 候选与评分层

把主题/角色转成多组查询，保存 `oracle_id ↔ print/set` 关系；先按硬约束过滤，再按主题相似、角色匹配、曲线、卡差、互动、协同和改动成本评分。输出 2-3 个带权重的 Pareto 方案，不声称存在单一客观最优。

### 4. 概率与规则层

先实现超几何/蒙特卡洛起手和前五回合资源模拟、基础地目标耗尽、传奇重复抽取；再接入成熟规则/对局引擎，不自行手写完整万智牌规则。

### 5. 对局反馈层

导入 Arena 日志或人工标注对局，记录版本、先后手、调度、换备、胜负和关键原因；只有样本量达标后才报告胜率或置信区间。AI 根据失败模式提出下一版 diff，人类确认后进入新版本。
